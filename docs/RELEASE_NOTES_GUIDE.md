# 发版规范

本文件记录 TokenMeter 发版时 **Release Notes 的写作标准**。目的：让每一位用户都能读懂"这次更新对我的影响是什么、我需要做什么"，而不是看到开发者自己的调试细节。

---

## 一、核心原则

> **Release Notes 是给用户看的公告，不是开发者的对账报告。**

写作前先问自己：**一个不认识仓库所有者、不关心实现细节的普通用户，看到这条能知道"这跟我有什么关系"吗？**

三条铁律：

1. **先讲用户会遇到什么，再讲怎么修好的**
   - ✅ "历史用量显示偏低，升级后自动修正"
   - ❌ "ScanCache 空桶污染，4001/6837 条目为空"

2. **说清"用户需要做什么"，多数情况是"无需操作"**
   - 需要重建索引 → 说明大概耗时、面板会有进度提示
   - 无需操作 → 明确写"无需任何手动操作"，消除顾虑

3. **技术细节点到为止**
   - 可以写"扫描失败的日志文件不再被误标记为已统计"
   - 不写具体实现（缓存版本号、并发队列、类名、函数名）

---

## 二、禁止出现的内容

| 禁止 | 原因 | 替代写法 |
|---|---|---|
| 开发者本机的具体数据（逐日用量、对账表格、亿数） | 其他用户看不到、也不关心，反而困惑 | 只说"偏高/偏低"，不列数值 |
| 第三方产品名做对比基准（如某个看板工具） | 用户不知道那是什么，像内部黑话 | 删掉对比，只描述自身行为正确 |
| 内部模块/类名（ScanCache、Aggregator、animator、FSEvents） | 用户无法理解 | 用功能描述代替（"索引""自动刷新"） |
| 开发流程信息（12 单测、CI 矩阵、commit 哈希） | 与用户无关 | 移除或压缩为不显眼的一行 |
| 只有开发者懂的缩写（harness、口径、zst） | 增加阅读负担 | 展开为"AI 工具""统计方式"等 |

## 三、结构模板

```markdown
## vX.Y.Z

### <emoji> <一句话主题：用户视角的变化>

<2-3 句话说清：以前是什么问题 / 现在变成什么样 / 用户会遇到什么>

**需要做什么**（如果无需操作，明确写"无需任何手动操作"）

### <emoji> <第二个主题>

...

---

### 其他
- 其它小改动（一句话一条）
```

### 标题写法

- ✅ "修复：历史用量统计偏少"
- ✅ "新增：侧边悬浮坞"
- ✅ "任务状态更准确：子任务不再误报已完成"
- ❌ "fix(cache): 空桶缓存污染根因修复"
- ❌ "悬浮坞 harness 任务条"

### 状态类功能建议用表格

三态指示灯、快捷键、可用范围这类"对照关系"，表格比长句更好读：

```markdown
| 指示灯 | 含义 |
|---|---|
| 🟠 橙色脉冲 | 正在运行任务 |
| 🟢 绿色 | 任务已完成，等待你查看 |
| ⚪ 灰色 | 空闲 |
```

## 四、涉及"数据修正"时的特别要求

当新版本会**改变已显示的历史数字**，必须说明：

1. **会变**：告诉用户数字会发生变化，避免误以为出 bug
2. **原因**：一句话（"部分日志此前未被完整统计"）
3. **耗时**：首次启动重建索引大约多久（如 3-4 分钟）
4. **提示位置**：面板会显示进度
5. **无需操作**：明确写出

**这些内部验证记录**（逐日对账、与其它工具比对的具体数值）应写进 **commit message**，不要进 Release Notes。

## 五、发版检查清单

发版前逐项确认：

- [ ] 每个小标题都是**用户能看懂的话**（不含内部术语）
- [ ] 没有出现自己机器上的**具体数字**和**第三方产品对比**
- [ ] 涉及**数据变化**的版本，已说明"耗时 + 无需操作"
- [ ] 新增功能说明了**在界面哪里**能找到
- [ ] 修复类说明了**修复前后的差异**
- [ ] 表情符号适度（每节 1 个），不刷屏
- [ ] 通读一遍：假设自己三个月后再看，还能看懂吗？

## 六、发布命令

```bash
./Scripts/install.sh <版本号>          # 构建 + 安装到 /Applications + 重启（本地验证）
./Scripts/release.sh <版本号> "<notes>" # 打 tag + 推送 + 构建产物 + 创建 Release
```

若需修改已发布版本的说明（拼写、措辞）：

```bash
gh release edit vX.Y.Z --notes-file /tmp/notes.md
```

## 七、README 与 docs 的分工

**README 是产品介绍页，不是开发手册。** 判断标准：只有使用者（装 App、看数据的人）需要的内容留在 README，其余一律下沉到 `docs/`。

| 留在 README | 移到 docs |
|---|---|
| 功能说明（用户能在界面看到什么） | 目录结构、模块划分 |
| 支持哪些数据源、统计口径 | 源码构建命令、脚本参数 |
| **安装步骤**（下载 Release → 拖进应用程序） | 发版流程（tag / 打包 / Release） |
| 自动更新的用户体感 | CLI 排查参数（`--timing`、`debug-activity`） |
| 价格估算的说明与自定义方法 | 缓存文件路径、`defaults write` 开关 |
| 已知限制 | 实验性功能（Tauri）的构建步骤、CI 说明 |

另外两条经验：

- **不要写开发机特有数字**（某台机器上看多少 GB、多少个文件、扫描多少毫秒）。用「几 GB」「零点几秒」这类量级描述，否则其他用户会对不上，也不该暴露个人数据。
- **安装章节不要出现 `./Scripts/xxx.sh`**。普通用户只按 Releases 下载；源码构建只留一行链接指向 docs。

## 八、历史修正记录

2026-11-11：
- v0.6.0 ~ v0.6.5 的 Release Notes 曾出现本机逐日用量对账表、第三方工具对比、内部术语等问题，已全部改写为用户视角。
- README 的「更新与发布」曾整段写发版流程与 `defaults write` 开关，已下沉到 `docs/DEVELOPMENT.md`；安装章节也从「跑 bash 脚本」改成「下载 Release 拖进应用程序」。
本规范即为防止此类问题再次发生而建立。
